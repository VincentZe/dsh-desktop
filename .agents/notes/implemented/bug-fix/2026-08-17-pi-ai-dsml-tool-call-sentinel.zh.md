# Agent Note：从 pi-ai 文本流移除回显的 DSML 工具调用哨兵

Status: implemented

[English](2026-08-17-pi-ai-dsml-tool-call-sentinel.md) | 中文

## 问题

一些 OpenAI 兼容网关会返回结构化函数调用，同时把 DeepSeek 工具调用结束哨兵 `</｜DSML｜tool_calls>` 回显为普通输出文本。Harness 会同时持久化这两类事件，因此即使工具调用已经正确解析，Web assistant 消息里仍会出现该哨兵。流式响应会把哨兵拆到多个增量中，所以在 session 或 Web 层做完整字符串替换无法阻止中间文本被发送。

## 决策

`llm-pi-ai` 在文本转换阶段只移除精确的结束哨兵。流转换器仅在文本末尾可能构成该哨兵前缀时保留后缀，其他文本立即输出；完整哨兵出现后会丢弃它后面的空白。文本块结束时还会对提供方的最终文本执行同样的精确移除。不完整或仅相似的字符串保持原样。

## 备选方案

**过滤 Web 投影。** 被否决，因为错误文本仍会留在持久化 session 中，其他消费者也仍会收到它。

**把所有自定义路由切换到 `openai-completions`。** 被否决，因为真实探针显示当前 endpoint 通过两个支持的协议都能返回结构化工具调用；协议选择属于部署配置，不能证明回显文本应由哪条协议负责处理。

**缓存每个完整的 assistant 文本块。** 被否决，因为这会让所有提供方响应都失去普通文本的流式效果。只缓存可能的哨兵后缀可以保持正常路径流式输出，同时覆盖跨事件拆分的哨兵。

## 后果

提供方适配器在内容进入 session 组装、Web 投影和其他消费者之前处理提供方线路上的伪文本。只有精确的结束哨兵及其紧随其后的空白会被移除；仅仅类似但不完整的哨兵文本会被保留。适配器不会推断或改写其他 DSML 语法。

## 测试

`packages/llm/llm-pi-ai/tests/convert.spec.ts` 覆盖被拆到三个文本增量中的哨兵、普通文本流式输出保持不变，以及不完整哨兵保持不变。针对 `deepseek-v4-flash-ga-260731` 的真实探针只输出脱敏后的协议结果，确认 `openai-responses` 与 `openai-completions` 都能返回结构化工具调用，因此没有把切换协议作为修复。完整 Web 复现依赖提供方的非确定性输出，没有固化为确定性 fixture。
